# Nomad Pocket — Architecture

Nomad Pocket is a standalone, offline-first mobile port of the ideas in
[Project N.O.M.A.D.](https://github.com/Crosstalk-Solutions/project-nomad): download
knowledge (Wikipedia, medicine, survival, books, courses), offline maps and a local AI
model once, then use everything with no connection. There is no backend: the app talks
only to public servers (Kiwix and its mirrors, Protomaps, Hugging Face, public Overpass
instances and this project's GitHub Releases) to download what the user chooses and, when
online, to check the two GitHub catalogs a few seconds after every launch (see External
services; the privacy policy in `site/privacy.html` lists the same hosts).

| NOMAD (server) | Nomad Pocket (device) |
|---|---|
| Kiwix serve + `.zim` | `modules/nomad-zim` — libkiwix/libzim native, `zim://` WebView |
| Kolibri courses | Educational ZIMs + app-side course progress (`features/courses`) |
| Protomaps `pmtiles extract` | `src/lib/pmtiles` — HTTP-range extractor in TS, MapLibre Native |
| Ollama + Qdrant RAG | `modules/nomad-llm` (Apple Foundation Models, iOS) + `llama.rn` GGUF (both platforms); RAG over libzim full-text search |
| Curated collections JSON | `src/data/catalog.json` + live Kiwix OPDS |
| Easy Setup wizard | `src/app/onboarding.tsx` + `features/onboarding/kit.ts` (country + one kit proposal) |
| Docker apps, benchmark | not applicable |

## Stack

- Expo SDK 58 (React Native 0.88, New Architecture, Hermes, React Compiler, typed
  routes), dev builds with Continuous Native Generation — `ios/` and `android/` are
  generated by `expo prebuild`, gitignored, never edited.
- Expo Router (`src/app`), native tabs (`expo-router/native-tabs`) and native stacks;
  pickers and confirmations are `formSheet`s.
- State: `zustand`. Persistence: `expo-sqlite` (tables, two files: `db()` and `indexDb()`)
  + `@/db/kv` (settings, map viewport, preparedness plan; the same store as
  `expo-sqlite/kv-store`, relocated off the Files-visible folder). ESLint bans importing
  `expo-sqlite/kv-store` or calling `openDatabaseSync/Async` outside `src/db`.
- Files: `expo-file-system` 58 (`File`, `Directory`, `FileHandle`, `DownloadTask`).
- i18n: `i18next` + `react-i18next`, one namespace per feature.
- Icons: `lucide-react-native`; tab bar uses SF Symbols / Material Symbols.
- Native deps: libkiwix 14.2.1 xcframework (iOS) / `org.kiwix:libkiwix:2.7.0` (Android),
  MapLibre Native via `@maplibre/maplibre-react-native` 11.5, `llama.rn` 0.13.0-rc.8,
  FoundationModels (iOS 26+, weak-linked). Android has no system model: ML Kit GenAI (Gemini
  Nano) was removed on 2026-10-26 (proprietary, sends diagnostics to Google), and Firebase is kept
  out of the APK (`plugins/with-android-no-firebase.js`).
- Other: `fflate` (gzip/zip), `@protomaps/basemaps` (style layers), `expo-network`
  (Wi-Fi checks), `expo-keep-awake` (map extraction, guidance), `expo-document-picker` (ZIM
  import), `expo-location`, `expo-screen-orientation` (compass heading in landscape),
  `expo-device` (RAM for model choice), `expo-haptics`, `expo-print` + `expo-sharing` (plan
  PDF), `expo-notifications` (local kit reminders only). Seven packages the app never used
  (`@expo/ui`, `@shopify/flash-list`, `expo-blur`, `expo-linear-gradient`,
  `react-native-webview`, `react-native-web`, and `react-dom` as a direct dependency) were
  dropped; `react-dom` stays installed as a peer of expo-router's web tabs, never bundled on native.
- Min OS: iOS 16.4 (Expo 58 floor), Android 8.0 (API 26). License: GPL-3.0-or-later
  (required by libkiwix/libzim); every bundled library's licence is in Settings › Credits &
  licenses (Credits below).

## Startup

1. `src/app/_layout.tsx` imports `@/i18n` (initialised with the device language), keeps
   the splash screen and calls `bootstrap()`. The root layout exports expo-router's
   `ErrorBoundary` (a crash in a screen shows a recovery screen, not a white one).
2. `features/bootstrap.ts`: imports `features/registry.ts` (each `register.ts` registers
   its completion handler, removal hook and init), opens the database (runs migrations),
   loads installed items into `useContent`, runs every registered init in order, then
   `initDownloads()` (restores the queue) and subscribes the "download finished" toast.
3. Feature inits:
   - library: create `Documents/content` and its subfolders, then exclude the root from
     iCloud backup (so the first session is covered too); after 500 ms, register loose `.zim`
     files in `content/zim`, backfill catalog metadata, warm up archives.
   - content (`content/register.ts`, `reconcile-core.ts`): 1 s after launch each installed
     item's file is probed (by stored path, then by name in its kind's folder); items whose file
     is gone (typically after restoring a backup: the database comes back, `content/` does not)
     are dropped with `removeItem(id, { keepUserData: true })` (bookmarks, history and course
     progress stay), with a once-only toast (`downloads.missing`). The world map is left to
     `maps/world.ts`; a truncated file is only logged, never deleted.
   - maps: load markers, delete stale extraction `.part` files, register loose `.pmtiles` and
     routing packs, copy the bundled world map; after 4 s: index maps whose index is stale,
     the detail around the user, sweep leftover routing/map files, resume interrupted side-file
     imports, and refresh the routing and maps catalogs from GitHub (unconditionally, whenever
     online; also each time a country screen opens). Each fetch tries 3 times with a 20 s timeout
     (`maps/catalog-fetch.ts`); the onboarding kit step tries again on arrival if it still failed.
   - assistant: engine lifecycle (release on background), system-model status watcher,
     chat sessions, forget a selected model whose file is gone.
   - prepare: notification handler (foreground banners) and tap → `/prepare/kit` (also from a
     cold start: the response waits for the navigator); expiry reminders are reconciled with the
     plan (startup, foreground, household or language change) through one queue.
4. The splash hides. Settings were hydrated when their store was created (synchronous
   kv-store read, `src/lib/kv.ts`); if `onboarded` is false the root pushes `/onboarding`,
   waiting until the navigator is ready (an early push is dropped).

## Data model (SQLite, `src/db`)

Two SQLite files, two accessors (`src/db/index.ts`): `db()` opens **`nomad.db`**, the user's
data and the content registry, and `indexDb()` opens **`search.db`**, the map search index and
the emergency points. Everything in `search.db` is derived from downloaded content and can be
rebuilt or fetched again, so it lives in the excluded-from-backup content folder and
`nomad.db` stays small. Only `src/db` opens databases (ESLint bans `openDatabaseSync/Async`
and `expo-sqlite/kv-store` elsewhere): use `db()`, `indexDb()` and `@/db/kv`.

**`nomad.db`**

| Table | Holds |
|---|---|
| `items` | Installed content of every kind (`zim` \| `map` \| `model` \| `route`): title, language, category, `is_course`, `file_path` (absolute URI), size, version, source URL, `catalog_id`, kind-specific `meta` JSON |
| `downloads` | Persistent download queue (same kinds): url, dest, bytes, `status` (queued/running/paused/processing/failed/done/cancelled), `pause_state` resume data, `meta` to register on completion |
| `history`, `bookmarks` | Reader state per (item, path) |
| `courses`, `course_progress` | Enrolled courses (syllabus JSON, last lesson) and manually completed lessons |
| `map_markers` | User pins (name, lat/lon, color, note) |
| `chat_sessions`, `chat_messages` | Assistant conversations, messages with cited `sources` JSON (retargeted when an archive's id changes) |

**`search.db`** (`Documents/content/index/search.db`)

| Table | Holds |
|---|---|
| `map_places` (FTS5) | Offline search index: `names` (indexed, `unicode61 remove_diacritics 2`), name, layer (place/poi/road), kind, lat/lon, `importance` (Protomaps min_zoom; `rank` is reserved by FTS5), `source` (map item id, `pois:<item id>`, `near:<item id>` (detail around the user), `places:<item id>` (a pack's or country map's named places), `streets:<item id>` (a country map's street names), or a routing pack's bare item id for its street names) |
| `map_localities` | Towns/neighbourhoods of the index (lat-indexed) for "Calle Mayor · Soria" context lines |
| `map_address_streets`, `map_addresses` | House numbers from a pack or country map: one row per street name key (`nameKey`) and source, one `WITHOUT ROWID` row per door (street, lat/lon in 1e-5°, number); ~22 B per door |
| `index_sources` | Per source: index version/zoom/date, plus the `places:<id>` / `addresses:<id>` markers of imported side files |
| `map_pois` | Emergency points per map item: OSM id (`n…`/`w…`/`r…`, or `t<lat>,<lon>` when taken from the tiles), kind, category, name, operator, phone, opening hours, emergency (ER yes/no) |
| `map_sources` | Per map item: emergency points fetch date/count (`pois_at`, `pois_count`) |
| `doc_passages` (FTS5) | The library's document index: passages (~650 chars, one page each) of the PDFs inside installed archives; `text` and `title` indexed (`porter unicode61 remove_diacritics 2`), `item_id`, `path`, `page` (1-based) |
| `doc_archives`, `doc_files` | Document index state: per archive the ZIM uuid and `DOC_INDEX_VERSION` it was built with, the PDFs found, `done_at`; per document its title, pages, pages with text, passages, status (done/locked/failed) |

Migrations: `MIGRATIONS` (user schema, v4 drops the index tables from `nomad.db`) and
`INDEX_MIGRATIONS` (v1 maps and points, v2 the document index) in `src/db/schema.ts`; `PRAGMA user_version` tracks what ran. Add one
by appending a SQL string; never edit an old one (the kind comments inside v1 are history,
the real list of kinds is `ContentKind` in `lib/storage.ts`). WAL mode.

**The split** (`migrate-core.ts`, pure, tested against real SQLite). Before the split there was one
`nomad.db` in `Documents/SQLite` holding both halves (up to ~1 GB per country of index), visible
in Files and backed up. The first time `db()` runs on such a phone, the user tables are copied
into a new `nomad.db` in the new location (row counts and `integrity_check` verified), renamed
into place, and the old file is *renamed* to become `search.db` (no big copy) and its user tables
dropped with `secure_delete` on its first open. Resumable after a kill; on any failure the old
file keeps working and the split retries next launch. The emergency points and their state follow
the same route. A renamed old index file keeps its free pages (`auto_vacuum` can't be switched
without a full `VACUUM`): they are reused by later imports but not returned to the system
(PROGRESS, known issues); fresh index files use `auto_vacuum = INCREMENTAL`.

**Key-value store** (`src/db/kv.ts`, same API and file format as `expo-sqlite/kv-store`; moved
with copy-compare-rename-delete): keys `settings` (zustand persist: `language`,
`contentLanguages`, `theme`, `wifiOnly`, `readerTextScale`, `onboarded`, `aiModelId`,
`country`), `prepare` (zustand persist, version 1: the whole emergency plan and kit, see
Preparedness), `assistant` (`chats.ts`: persists `useLibrary`), `maps.viewport`,
`maps.routingManifest` and `maps.countryManifest` (cached catalogs), `maps.detailIndex` (centre
of the detail index), `maps.sideImports` (side files still to import),
`maps.pendingIndexDrops` (index rows of removed maps still to delete) and
`reader.disclaimerDismissed.<itemId>`. Persisted stores use `kvStorage()`
(`src/lib/kv.ts`): reads use the sync API, so the stores are hydrated when they are created and
the root layout doesn't wait for hydration (with expo-sqlite's own kv-store, an async first open
racing a sync read once left the settings hydration hanging and the setup wizard never showed);
writes stay async.

```

    maps/<key>.pmtiles     key = region id, 'world' or 'area-…'
    routing/<id>.tar       Valhalla tile extract (routing pack), id = region id
    models/<file>.gguf
    index/search.db        map search index + emergency points (derived, re-downloadable)
    partial/               in progress: <id>.part, map-<key>.pmtiles.part, import-<ts>.zim.part
  map-assets/v4/           glyphs + sprites unpacked from the bundled zip (excluded from backups)
```

Backups (iOS, Android cloud backup and device transfer alike): **included** are the kv-store
(settings, family plan, kit) and `nomad.db`; **excluded** are `content/` and `map-assets/`
(`plugins/with-android-backup-rules.js` writes the Android rules: an include of `SQLite/` only, so the
rest of filesDir is left out without excludes, which Android lint rejects outside an include; iOS
marks `content/` and `map-assets/` excluded at startup). After a restore the registry rows come back without their files:
`content/register.ts` drops them at the next launch (Startup). Old installs had the databases
in `Documents/SQLite` (Files-visible): `removeEmptyLegacyDir()` removes that folder once the
move is done.

`app.json` enables `UIFileSharingEnabled` + `LSSupportsOpeningDocumentsInPlace`, so
users (and the E2E suite) can drop `.zim` / `.pmtiles` files into `content/`: they are
registered at the next launch. iOS changes the container path on reinstall/update:
stored URIs are re-anchored with `resolveContentUri()` (anything under `/content/`).
`hasRoomFor(bytes)` keeps 500 MB of headroom; `freeBytes()` counts space iOS can purge
(important-usage capacity) and the user-available blocks on Android.

## Cross-feature contracts

### Content registry (`src/features/content/items.ts`)
- `upsertItem(input)`, `getItem(id)`, `listItems(kind?)`, `removeItem(id, { keepUserData? })`
  (runs the kind's removal hook, deletes the file and its history/bookmarks/courses rows;
  `keepUserData: true` keeps those rows, used when a file went missing),
  `onItemRemoved(kind, hook)`, `useItems(kind?)`.
- ZIM items backed by the catalog read title/description from the catalog in the current
  app language (the list refreshes on `languageChanged`).
- Ids: ZIM = catalog id (`wikipedia_es_top_mini`), else the ZIM `Name`/UUID (an archive the
  catalog doesn't know takes its flavour from the file name, `fallbackZimId`); map =
  `map-<key>`; model = model id (`qwen3.5-2b-q4km`).

### Downloads (`src/features/downloads/manager.ts`)
- `enqueueDownload({ id, kind, title, url, filename, expectedBytes, meta, group?, integrity?,
  quiet? })` — no-op if the id is already active; `filename` goes through `safeFileName` (never
  a path); checks free space including what queued downloads still need plus the reserve
  (`NotEnoughStorageError`, whose figure adds up); persists; how many run at once is the
  connection budget (below).
- **Connection budget** (`budget-core.ts`, pure; sampled in `manager.ts` every 2 s while
  something runs): one budget of connections for every URL download (a single transfer counts
  one). Wi-Fi starts at 16 (8–32), mobile data at 4 (2–6); a change of network type resets it.
  Every 10 s window in which the downloads used it all, it tries +4 and keeps them unless the
  total speed fell below 90 % of the speed before, else gives them back and waits 1 min (it used
  to keep them only on a ≥ 15 % gain: past 14 connections 2 more can't give that, and the mirrors
  swing ±40 % between windows, so on a phone it sat at 10–14). A window in which a download
  started or ended (hashing, probing dip the speed), that began less than 5 s after such a
  change (new transfers still ramping up), or that spans an iOS suspension, decides nothing. Up to 6 files run at once on Wi-Fi
  (2 on mobile data), at most 2 still choosing their sources, and at most 2 from one
  single-host source (`hostHasRoom`: a country's GitHub parts share that host's connections,
  so a third part would only take a slot from a kit's Kiwix archives, which spread over many
  mirrors; the queue then starts a later file instead). Each segmented download takes what the
  others leave, or only its fair part while another wants more (`connectionsFor`).
- **CDN files first** (`yieldsToCdn`): a Kiwix archive of 1 GB or more doesn't start while the
  GitHub / Hugging Face files running or ready to start still have 300 MB or more to fetch. All
  ranges to one of those hosts travel in **one HTTP/2 connection** (URLSession and OkHttp
  multiplex them), which on a full line gets about one connection's share next to 20+ to the
  mirrors (an iPhone: Spain's map at ~7 MB/s for 5.5 min beside Wikipedia, 57 MB/s alone).
  One after the other the total is the same, and the map and its search imports come first.
- **Wi-Fi only is enforced in the manager**, not by callers (`manager-core.ts`, pure):
  `networkGate()` reads `expo-network` (state + listener; reads carry a sequence number so a
  late iOS answer can't undo a newer one) and the setting. A held record stays `queued` and the
  UI says "Waiting for Wi-Fi" / "Waiting for a connection"; a running transfer that lands on
  mobile data pauses into the same state with its resume data. One question per batch (a
  country or a kit is one batch, `wifi-prompt.ts`): wait for Wi-Fi, or use mobile data for
  these downloads only (`meta.allowCellular`; rows and the Downloads sheet offer the same).
  `downloadResource`/`downloadModel` don't throw for mobile data any more (`OfflineError`
  stays). `EnqueueInput.quiet` marks automatic downloads (a missing search file), which never ask.
- **Sources** (`mirrors.ts`, pure): every run starts with `planSources()` (pause works while
  it probes: a run token). A download.kiwix.org file: its `.meta4` metalink, then **every**
  https mirror is measured at once by throughput (up to 4 MiB from a random offset, bytes
  counted for 2 s from the first byte, through `expo/fetch`, which streams) and ranked; the
  quickest to answer is often a slow one. Any other URL (GitHub Releases, Hugging Face) is one
  source, asked a one-byte range to learn whether it takes ranges and its exact size. The
  metalink's `<size>`, sha-256 and 4 MiB sha-1 `<pieces>` are kept. The finished file is
  checked against size + sha-256 (`modules/nomad-files` `sha256`, native, 4 MiB blocks; not `File.digest`: see below); a bad copy is deleted,
  the row says it is damaged and the retry avoids that mirror (single transfers only: a
  segmented file has many). Manifest downloads pass `EnqueueInput.integrity` (size + sha-256)
  and get the same check. Mirror speeds are remembered by host for 10 min (in memory,
  `known`): a file whose mirrors were all measured recently starts without probing, which a
  kit of twenty small archives needs.
- **Segmented engine** (`segmented.ts`, decisions in `segments-core.ts`, pure): used when the
  file is ≥ 4 MiB, of known exact size, and its sources answer ranges with 206. Ranges of
  4–32 MiB (~48 per file, whole metalink pieces), each a `DownloadTask` with a `Range` header
  into `partial/<id>.chunks/<start>-<end>.<n>`. Connections come from the budget; per host at
  most 3 to a Kiwix mirror and 12 to a single URL, summed over every download.
  On iOS the ranges run in the **in-process (foreground) URLSession while the app is open**: in
  the background session (nsurlsessiond) an iPhone 14 Pro got ~25–45 MB/s in all on a 66 MB/s
  Wi-Fi and ranges waited at 0 % for 1–3 min. A range with no byte for 15 s (`STALL_MS`, checked
  every 5 s) is cancelled and counts as an error of its source.
  A free connection takes the lowest missing range and the source whose connections measured
  fastest (moving average; an unmeasured mirror gets one range to prove itself; sources under
  25 % of the best get none: the default Kiwix mirror, 0.4 MB/s, held the head for ~90 s). Two errors in a row bench a source for 2 min; a 4xx or a server
  ignoring `Range` (iOS accepts any 2xx: the guard cancels when `totalBytes` isn't the range's
  length) rules it out; 6 failures in a row with no progress end the run, and
  `planAfterFailure` takes over. When nothing new can start and the range the file waits for
  crawls (3× slower than the best source would be), it is fetched again elsewhere and the
  first copy wins.
  Finished ranges are appended **in order** to `partial/<id>.part` (`modules/nomad-files` `copyInto`, native, 4 MiB
  blocks, each metalink piece's sha-1 checked natively on the way; a corrupt range
  rules its mirror out and is fetched again, more than 3 fail the download). So the `.part`
  is always a verified prefix (`validPrefix`: whole chunks only) and, with the range files
  already on disk, the whole resume state: nothing in `pause_state`, `meta.segments` holds
  size and chunk size. Ranges may finish up to 2 GiB past the prefix (less when the disk is
  short; 1 GiB filled behind one slow range with 16+ connections). Pause/hold = cancel the ranges
  in flight; resume = schedule the missing ones. When every piece was checked in this run
  (`piecesChecked`: metalink pieces for the whole file, started from zero) the whole-file sha-256
  is skipped (`meta.piecesChecked`): it added 10 s for 13 GB at the very end.
- Everything else (small files, no ranges, a record paused with iOS resume data) is one
  `DownloadTask` from the best source, `sessionType: 'background'` (iOS keeps going in the
  background). A `.part` written segmented never continues as a single transfer (its bytes
  past the last whole chunk aren't trusted): it starts over.
- **Keep awake** (`keep-awake.ts`): while a record is `running` or `processing` and the app
  is active, the screen stays on (tag `downloads`; the Downloads sheet says so). On Android a
  locked screen sends the app to the background, which pauses every download.
- **Big files never go through JS or `File.digest`** (`modules/nomad-files`, Swift + Kotlin):
  `sha256(path)` and `copyInto(src, dst, offset, pieces?)` read 4 MiB blocks, each inside its
  own `autoreleasepool` on iOS. expo-file-system 58's `File.digest` reads in one native loop
  with no pool, so every block stays alive until it ends: hashing a 2 GB map part held 2 GB and
  iOS killed the app ("jetsam per-process-limit", an iPhone 15 Pro, build 14, Spain's map in
  "Preparando", and again at every launch since the manager resumes `processing`). The
  segmented engine's appends and the country map / routing pack assembly use `copyInto`.
- Failures (`planAfterFailure`, `manager-core.ts`): network errors and 5xx keep the bytes and
  retry with backoff (5 s, 30 s, 2 min); only stale state (invalid resume data, 4xx on the
  range request) restarts from zero. Android continues from the `.part` length; the saved
  `.part` path follows iOS container moves.
- Android stops transfers with the process: on background the manager pauses running
  tasks and stores their resume data (segmented ones: cancels their ranges), and pumps the
  queue again on foreground. iOS: when the app turns `inactive` (just before it leaves the
  screen) a segmented download queues up to 4 bigger ranges (256 MiB) in the background
  `URLSession` as a reserve (`prepareBackground`): a background-session task created once the app
  is in the background is discretionary, and that reserve got no byte in 100 s on an iPhone on
  power and Wi-Fi. On `background` its foreground ranges are dropped; each finished background
  range is acknowledged (`deferBackgroundSessionCompletion`) only after it started the next ones,
  so a background wake-up keeps it going. Back in the foreground, background ranges that never
  started are dropped without blaming their mirror. Measured: ~1 GB in 2 min of background, full
  speed again ~10 s after the return.
- **Field traces** (`trace.ts`): `[dltrace]` lines in the system log (also in Release; on a
  phone `idevicesyslog -p NomadPocket`): each file's start, source choice, move, hash and
  install times, and every 10 s the total speed, connections and each segmented download's
  state (ranges in flight, waiting behind the prefix, the head range, per-mirror slots).
- Relaunch: downloads with stored resume data (paused, or snapshotted on Android
  background) resume; segmented ones continue from their `.part` prefix and range files,
  even after iOS terminated the app (the orphaned range tasks fetch at most what was in
  flight again); single transfers without resume data go back to the queue and restart from
  zero on iOS (the background session isn't reattached, see PROGRESS known issues); a
  download that died while `processing` with its file in place is finalised; orphan `.part`
  files and `.chunks` dirs are swept.
  After a backup restore `downloads` rows come back but `content/partial` does not: a queued,
  running or paused segmented download (`meta.segments`) with neither `.part` nor `.chunks`, or a
  `processing` one with no file anywhere, is marked `failed` with error `PARTIAL_LOST`
  (`restore-core.ts`, row text `downloads.error.restored`), so nothing re-downloads gigabytes
  behind the person's back; their Retry restarts it from zero. Rows that never started and single
  transfers (< 16 MB) are left alone.
- Completion: `.part` → `content/{zim,maps,models,routing}/<filename>` → the kind's handler registered with
  `registerCompletionHandler(kind, async (file, record) => …)`, which must `upsertItem`; a file
  the handler rejects (throws) is deleted. Then `onDownloadFinished` listeners (toast) fire.
- Groups: `enqueueDownload({ …, group: { id, title } })` (stored as `meta.group`) marks
  files that make one thing; a country is `countryDownloadGroup(regionId)` (`country-<id>`;
  map parts, routing pack parts, points, streets, places, doors). `groupDownloads()` (`groups.ts`,
  pure) turns records into rows: the Downloads sheet and the home card show "Mapa de
  España" with the summed bytes and one set of buttons (`pauseDownloads`,
  `resumeDownloads`, `cancelDownloads` act on the whole row). A group's finished files stay
  in the store until the last one is done, so its total holds steady, and the listeners
  fire once, with the group's title. `cancelDownloads` cancels a member in `processing` only
  when its `meta.abortable` is set (`EnqueueInput.abortable`; decided by `cancelAction` in
  manager-core): country map and pack parts are, and their assembly aborts, registers nothing and
  deletes its parts.
- `pauseDownload`, `resumeDownload`, `cancelDownload` (deletes the partial file),
  `dismissDownload`, hooks `useActiveDownloads()`, `useDownload(id)`.
- `startExternalJob({ id, kind, title, totalBytes, cancel })` → `{ update, finish, fail }`
  for non-URL work (map extraction) so it shows in the same downloads UI.

  were invisible to search and the assistant. Each archive is read once in the background: native

  then `getPdfText(id, path, 1500)` per document (the entry is copied to a temp file a few MB at a time;

  duplicate passages (the same guide in two archives). Measured on a Mac: extraction ~35 s for the six
  guides with PDFKit, 68k passages, 62 MB in `search.db`, 1–5 ms per question.

### Maps (`src/lib/pmtiles`, `src/features/maps`, `src/app/(tabs)/maps`)

**Extractor** (`src/lib/pmtiles`, pure TS, no `@/` aliases so `node --test` loads it):
`readArchiveInfo`, `planExtract(source, { bbox, minZoom, maxZoom, overfetch, signal,
onProgress })` → `ExtractPlan` (exact archive size + download size; this *is* the
dry-run estimate), `executeExtract(source, plan, sink)`, `extract()` = both.
I/O is injected: `RangeSource` (`FetchSource` = HTTP Range with retries and ETag
pinning via `If-Match`; `BytesSource` for tests) and `Sink.write(offset, bytes)`
(app: expo-file-system `FileHandle`; tests: memory / `node:fs`).

How it works (same idea as `pmtiles extract`): bbox → Hilbert tile-id ranges per
zoom via quadtree descent (descendants of a tile form one contiguous id range, so
ranges are O(perimeter)); walk the root directory and fetch only the leaf
directories whose id span intersects the ranges (coalesced); collect entries,
deduplicate contents by source offset (keeps the output clustered), lay out
`header | root | metadata | leaves | tile data`, rebuild directories (root ≤ 16 KiB,
gzip via fflate) and coalesce tile byte ranges (merge smallest gaps while overfetch
≤ 5 %, requests ≤ 4 MiB). Tiles are written straight to their final offsets, so
downloads run 4 at a time out of order. Measured against build 20261023: world
z0–5 15 MB (2 s plan), central Madrid z0–15 10.7 MB, Comunidad de Madrid z0–14
58 MB, Spain z0–14 1.6 GB (plan 4 s, 2.9 MB of directories). Areas above 2.5 M tiles
are refused (choose less detail).

**Extraction jobs** (`extraction.ts`): `latestBuild()` reads
`build-metadata.protomaps.dev/builds.json` (cached 6 h) → `build.protomaps.com/<YYYYMMDD>.pmtiles`;
`estimateExtract` caches plans; `startMapDownload({ key, title, bbox, minZoom, maxZoom,
regionId, estimate })` runs as an external download job on the JS thread with the screen
kept awake, writes `partial/map-<key>.pmtiles.part`, moves it to `content/maps/<key>.pmtiles`
and upserts `{ kind: 'map', id: 'map-<key>', meta: { role: 'world'|'region', bbox,
minZoom, maxZoom, buildDate, regionId, bundledPoints } }`. Only the fallback for a country
the maps catalog doesn't have: `bestZoom(bbox)` = 15, lower only above 2.5 M tiles. **Resume after a kill** (pure
bookkeeping in `extraction-core.ts`): the plan is deterministic for a pinned build + bbox + zooms, so
the kv key `maps.extractions` keeps each running job's inputs, the planet build it started with, a
fingerprint of its plan and the indices of the tile requests already written to the `.part`
(run-length text, saved at most every 1.5 s; `executeExtract` takes `done` / `onRequestDone`). At
startup `resumeMapDownloads()` (from `register.ts`, in a `setTimeout`) re-plans against the saved build
(a few seconds), skips the finished requests and continues in the same `.part`; the saved progress is
void (start over) if the server no longer has that build, the plan's shape differs or the `.part` is
shorter than what the finished requests wrote. Cancel and failure delete the `.part` and the saved job;
`.part` files without a saved job are deleted at startup. `EXPO_PUBLIC_PLANET_BUILD_URL` (dev/E2E) replaces
the Protomaps build with `scripts/dev-planet-server.ts` (synthetic planet with Range and a delay;
`PLANET_PORT` in `scripts/e2e.sh`, flow `map-22-extract-resume`). Loose `.pmtiles` files
are registered at startup from their header (`register.ts`; a region id as file name
gives the region's name).

**Country downloads** (`countries.ts`, `country-maps.ts`, pure `country-core.ts`; plan in

picker by owner decision). A country = its map + its routing packs (`routePacksFor`: those with its

for there, only for such a country). Without `regions`, a retry or an update covers the
regions on the phone or on their way. `CountryState.maps`/`regions` list them;
`removeCountryRegion` deletes one (the last one takes the country). A route between two US
regions is stitched at a crossing of the region border, as between countries (Routing below;
docs/ROUTING_ACROSS_PACKS.md). Canada and Russia are split for the map only (`ca-ontario`,
`ru-south`…: regions without a pack): their national pack is `CountryOffer.common`
(`countryWidePacks`), planned with any non-empty choice of regions and removed with the last
one, so routes between their regions work; `partAt` tells their regions apart by the map's
outline cells (`CountryMap.cells`). Maps that aren't a country (older community/state or visible-area maps) are
listed as "Otros mapas". **Prebuilt maps**: `.github/workflows/country-packages.yml` (monthly, or by hand with a
country list and `parts` = all / maps / routing; one job per country builds its routing pack
first, see Routing, then its map, and the run publishes both catalogs and prunes both families
of releases; the jobs live in `country-build.yml`, called twice with half the list each: GitHub
refuses a matrix over 256 jobs and a full run has 261)
runs `scripts/maps/build-country-map.sh` per country: `pmtiles extract` of the planet build
over the country's outline (`country-region.py`: Natural Earth 10m polygons with islands and
exclaves within 10°, grown 5 km; Spain then carries Canarias and no Portugal: 2.3 GB instead
of the bbox's 3.2 GB; Natural Earth is pinned — v5.1.2, commit f1890d9 + sha256 — and a failed outline
fails the job; the `regions.json` bbox is used only for countries Natural Earth lacks) at z15 (the highest zoom whose archive is ≤ 10 GB), split in
≤ 1900 MiB parts. A country split in regions (packs.json `region`: the USA in us-west, us-midwest,
us-northeast, us-south, us-alaska, us-hawaii) gets one map per region instead (`id` us-west,
`regionId` us; `region-outline.py`: the region's Geofabrik `.poly` ∩ every Natural Earth polygon of

**Country download lifecycle** (`countries.ts`, `country-maps.ts`, `routing-packs.ts`,
`side-files.ts`, pure `country-core.ts` / `routing-core.ts`):
- *Before queueing*: `planCountry` / `countryNeed` work out the room needed (assembly copy plus the
  queued downloads) in one check before anything is queued; the copy is the biggest multi-part archive
  only, because assemblies (maps and packs) run one at a time (`assembly.ts`); a refused enqueue cancels what already
  went in. A country's records are grouped as `country-<id>` (Haiti and the Dominican Republic share
  a pack). Automatic re-fetches are quiet (no mobile-data question).
- *Catalogs*: both manifests are validated before use (`parseManifest` and its maps twin reject paths and other URL schemes in names
  and URLs). Every map or pack part and side file is enqueued with its size and sha-256
  from the manifest (`fileIntegrity()`), verified by the manager. `ENGINE_VALHALLA` (`routing-core.ts`,
  major.minor gate) is the Valhalla version the app reads: a catalog built by another version offers
  no packs, and an installed pack from another version reads as outdated. Bump it together with
  valhalla-mobile and `VALHALLA_IMAGE`.
- *Assembly*: appends the parts into `<regionId>.pmtiles` / `<id>.tar.tmp` and registers the item. With
  parts missing it waits for active or failed ones, re-queues parts nothing will bring (same build) or
  fails if the catalog moved on; it never reports success without a map. Removing the country during
  assembly aborts it: nothing is registered and its files are deleted. A failed record keeps its files
  (a retry continues); the startup sweep keeps the side files of installed items.
- *Side files* (`side-files.ts`): points, streets, places and doors are imported one file at a time
  through a queue; the kv marker `maps.sideImports` lets a startup replay the `.tsv` files still on
  disk after a kill; 3 attempts, then it gives up (the next catalog refresh re-fetches a missing map
  side file or pack POIs file). Large files are read in blocks of whole lines (`forEachLineBlock`).
  Streets, places and doors go to SQLite as JSON (`import-core.ts`): each 1 MB block becomes one
  JSON string (four string replacements in JS) that `json_each` parses into a temp table on the
  index file's background connection, and the inserts read from there; JS only computes `nameKey` /
  `houseNumberKey` once per distinct street and number, and `indexText` for rows that may hold CJK.
  Parsing row by row in Hermes took ~2 min of the JS thread for Spain (5 M rows) and the app
  stuttered; `import-core.test.ts` checks the SQL path writes the same rows as the TSV parsers
  (also checked on Spain's full files). Emergency points (tags decide the kind) are still parsed in
  JS, in 512 KB blocks, and written as JSON statements. They stop when their map is removed.
- *Preparing* (`prepare.ts`, pure `prepare-core.ts`): once a country's bytes are in, its maps and packs
  still have work queued: the tile index (`scheduleIndex`, weight ~10 KB per tile), each side file's
  import (weight: its size, progress by bytes read) and, for a map without bundled points, its
  Overpass points. Each registers a task when queued; an item's tasks stay until all are done, so the
  country's `preparing` (0–1, `useCountries`) never goes back. The country shows "Preparando… %"
  (countries sheet, Home card and readiness, Downloads, onboarding badge, search sheet) and is only
  ready, with the "listo para usar sin conexión" toast, after it.
- *Updates*: a pack update compares `buildDate`, downloads the new tar and replaces the pack, closing
  the router once the new file is in place (`closeRouter()` in `routing.ts`, serialised);
  `NomadRoute.open()` reopens when the file's inode/size/mtime changed.

**Search index** (`places.ts`, pure parts in `places-core.ts`, `src/lib/mvt/decode.ts`,
`src/lib/pmtiles/reader.ts`): every installed map is decoded once into `map_places`
(FTS5, in `search.db`) — `places` (towns, neighbourhoods, countries), named `pois` (except street
furniture) and named `roads` (one row per name and tile; deduped within 1.5 km at query
time). Reads one zoom: the archive's max zoom capped at 15, lowered until ≤ 40 000 tiles
(`pickIndexZoom`; Spain at z14 is indexed at z12, so minor streets are missing there);
the world basemap at z5. A map whose country brings search files (`bundledSearch`, set at install
from the catalogs in `register.ts`: its own or a pack's `places`) is read at z10 at most: the files
hold every named place and street, the tiles add islands, regions and towns at a fraction of the
tiles. A queue indexes one map at a time, decoding tiles for 12 ms, then inserting them as one JSON
statement on the background connection and yielding (`LocalFileSource` also yields every 12 ms
while listing a big archive's directories). Every bulk delete runs there too: a `DELETE … WHERE
source = ?` reads the whole FTS table, which on the JS thread froze the app for seconds. Triggers: 4 s after startup for maps whose `map_sources.index_version`
≠ `INDEX_VERSION` (bump it when `tileRows` changes), and `onMapInstalled` after a download
(re-index). Index writes take turns (one transaction at a time). Removing a map cancels its job and deletes its
rows off the JS thread in one transaction; a removal a kill cut short is finished at the next launch
(kv `maps.pendingIndexDrops`). **Detail around the
user**: at the indexed zoom a big map has only its important POIs (Spain at z12: no
schools or shops), so the map's own max zoom (≤ 15) is also indexed over a 50 km square
(`listZoomTiles(…, { bbox })` walks only the leaf directories over it; ~700 tiles at z14)
under `near:<item id>`: around the user 4 s after startup and after a map install (last
known position, or one coarse fix on a fresh install; only with permission already
granted, else the last viewport) and around the map centre when the search sheet opens
(viewports at zoom ≥ 9 only: a world view says nothing about where the user looks). It is redone when that point is ≥ 10 km from the last centre
(kv-store `maps.detailIndex`); duplicates of the whole-map rows merge in `rankHits`. Skipped for
maps their country's search files cover (`searchFilesCover`: `bundledSearch`, or an installed
places file of the map or a pack of its country): it ran when search opened ("Preparando la
búsqueda", ~10 s for Madrid at z15) and added nothing those files don't have.
`searchPlaces(text, near)` runs on a second read connection (`getAllAsync`; the sheet
debounces 200 ms and a newer search cancels the older) and caps the matches before ranking (20 000
for queries under 3 letters, 50 000 otherwise, ordered by importance). Chinese and Japanese runs are
indexed as overlapping character pairs and matched as a phrase, so a name is found from any part of
it; rows indexed before that change only match from their first character until the map is
re-indexed (`INDEX_VERSION` was not bumped). The match = FTS prefix match (`"word"*` per word, ANDed; address
abbreviations also match their word: `("avda"* OR "avenida"*)`, `ABBREVIATIONS`) →
`rankHits` (exact > prefix > word match with "de/la/…" left out, against every name variant of the row,
so a city typed in English or Spanish ranks as exact; place > POI > street, importance, log-distance from
the map centre; ranked by `rankKey`, `nameKey` without apostrophes, and deduplicated by it with
`dedupeHits`, which stops at the limit: pairwise keys over thousands of rows froze "farmacia") → nearest
locality as context. A word ending in s also matches its possessive ("mcdonalds" → McDonald's, which FTS
holds as `mcdonald` + `s`). Tile rows keep their name variants in slots of `names` separated by `NAME_SEP`
(U+001F, a space to the tokenizer): native, name:es, name:en, the rest (`INDEX_VERSION` 2); the search rows
and the place card show `localizedName` (the app language's name, the native one as subtitle; Spanish
falls back to English only for a non-Latin native name). Pack rows get the same slots when their side files carry
the trailing name:es / name:en columns (packs built from 2026-10-29: `packNames`, and the same in SQL in
`import-core.ts`); older files keep plain names until their pack updates. A door found on a street
(`doorHits`) gets ", <number>" in every slot (`namesWithNumber`). A query that is only a category word (`categoryKinds`: "hospital",
"farmacias", "pharmacy", "agua potable", "farmacia cerca"…, es + en) puts the nearest `map_pois` of those
kinds first (`nearestOfKinds`, growing radius), before the name matches. A query that
reads as an address (`parseAddress`: "Calle Alcalá 50", "Alcalá, 50", "50 Alcalá") also
brings the streets matching its street part, after the full-text hits, and before them
the door itself on the best 8 of those streets (`doorHits`: the pack's house numbers of
that street name within 3 km; `locateHouseNumber`: the door, else between the nearest
numbers on the same side, else the nearest number ≤ 10 away; kind `address` /
`address_approx`). Japan has no streets in its addresses (blocks inside a chōme):
`parseJapaneseAddress` reads "台東2丁目5-1", "台東2-5-1", "台東二丁目5番1号" (also after the
prefecture and city) as the street "台東2丁目" + number "5-1" that places.py writes from
`addr:quarter` + `addr:neighbourhood` + `addr:block_number` + `addr:housenumber`, and
`japaneseDoorHits` looks the door up by that key directly (else any door of the block,
approximate). The search sheet
also matches saved places and parses coordinates (`geo.ts`: decimal, DMS with N/S/E/W/O,
UTM with band letter). House numbers come only from a pack (Protomaps tiles carry none).

**Boxes across the antimeridian.** A `[west, south, east, north]` box with west > east (Fiji,
Chukotka, the Aleutians), or with a longitude past ±180 (a box around a point near 180°), is
handled in `geo.ts`: `lonRanges` cuts it in two, `lonSql(column, w, e)` builds the SQL
condition (`BETWEEN` or two joined by `OR`), `nearOrderSql` keeps nearest-first ordering right,
and `bboxHas` / `bboxesOverlap` are the in-memory checks (routing pack coverage, country parts,
detail indexing). Never write `lon BETWEEN w AND e` or `lon >= w && lon <= e` by hand.
`splitBBox` (Overpass cells) cuts at 180° too. Pack coverage from tile names
(`tileCoverage`) still reports a -180..180 bbox for such a pack; its 1° `cells` make it exact.

**Emergency points** (`emergency.ts`, pure parts in `emergency-core.ts`): 17 kinds in 5
categories (health, security, water & shelter, supplies, institutions) from OSM tags.
After a region download (and from the Emergencias sheet) the app POSTs an Overpass query
for the region's bbox, split into ≤ 3° cells (a 3° cell over central Spain: ~60 s, 25k
points; Comunidad de Madrid: 15k points, 1.2 MB TSV), to three public servers in turn,
with a per-request timeout (query timeout + 30 s; servers that are at capacity hold the
connection). TSV output (`[out:csv]`) keeps it small. Rows replace the region's
`map_pois` (in `search.db`) and go into the search index under `pois:<item id>`. Offline fallback: while
indexing, emergency-kind POIs found in the tiles (named or not, e.g. drinking water) are
stored as `t…` rows unless the region already has Overpass points — at z15 that is most
of them, at z12/14 only the important ones (Protomaps gives most POIs min_zoom 15–17).
Queries: `nearestEmergencyPlaces(category, from)` (equirectangular ORDER BY, GROUP BY
osm_id across overlapping regions; the nearest 3 of each `PRIORITY_KINDS` kind lead the list,
hospitals in Health, police and fire stations in Security, so 40 closer pharmacies can't hide the
nearest hospital: `mergePriority`), `emergencyPlacesIn(bbox, hidden, zoom)` for the map layer (zoom ≥ 11,
at most 600, hospitals/police/fire first, then by category; below z17 `thinForZoom` keeps one point per
kind per ~48 px cell, hospitals, police, fire and ambulance stations always). The Puntos sheet (`maps/points.tsx`, the
three-dot map button) is its legend and settings: `settings.mapPoints` hides the layer,
`settings.hiddenPointCategories` leaves categories out *in the SQL*, before the limit, so the others fill it.
`emergencyNumber()`: 911 for the device region in most of the Americas, else 112.

**Routing** (`modules/nomad-route`, `routing.ts`, `routing-packs.ts`, pure parts in
`routing-core.ts`, `valhalla-defaults.json`): Valhalla 3.9.1 on the device through
Rallista valhalla-mobile 0.6.4 (MIT). iOS: the static xcframework + `tzdata.tar` are
fetched by `modules/nomad-route/scripts/fetch-ios-libs.sh` (postinstall, sha256-pinned);
`NRRouter.mm` calls only the wrapper's plain functions (`create_valhalla_actor`, `route`,
`matrix`) and **includes no Valhalla header** — inline templates instantiated in our file
won over the library's at link time and every tar search came back empty (171) while
loose tiles worked. Swift untars `tzdata` into `Library/tzdata` on first open. Android:
Maven `io.github.rallista:valhalla-mobile:0.6.4` (`Valhalla(configPath).routeRaw`).
Isochrones are not exposed by either wrapper (later). **Request tuning** (`routeRequest`,
each checked against a local Valhalla 3.9.1 on Madrid's and Andorra's graphs, 2026-10-25):
by car both ends snap with `search_filter.min_road_class: residential` (inside a block the
nearest edge was the garage aisle under the building, destination-only but still a valid
start, and routes "left" through the garage); every end except a reroute's origin also has
`exclude_tunnel` (above Plaza de España's tunnel the start snapped into it); on foot
`max_hiking_difficulty: 2` (Valhalla's default 1 cut off mountain trails: a hut 3.6 km
away by the trail became 6.4 km to the wrong place). Driveways and parking aisles get no
car-cost penalty in 3.9.1 (only generic service roads do) but are destination-only, so
through routes avoid them; `date_time` changed nothing on central Madrid trips (not sent).
The module takes a config JSON
(`valhallaConfig(defaults, tar)`; native writes it to a file per pack) and request JSON;
errors come back as `valhalla <code>: <message>` (`routingErrorKind`: 171 no road near,
442/170 no path, 154 too far). A **routing pack** is a Valhalla tile extract
(`content/routing/<id>.tar`, mmapped, never unpacked), item kind `route`; its coverage
(`meta.bbox` + `meta.cells`, the 1° cells holding its local-road tiles — a bbox
over-claims: Spain's covers Portugal) comes from the manifest or, for loose files, from the
tile names in the tar (`tileCoverage`). `computeRoute(from, to, costing)` tries the packs
covering both ends, smallest first, moving on after "no road" / "no path" (packs are
whole countries; packs installed from the first catalogs may be Spanish regions, tile
subsets of the country build, which lack the roads a trip needs past their edge). Engine calls are
serialized in JS (open + route never interleave with another request or a close).
**Routes across packs** (`stitch-core.ts`, pure, tested; docs/ROUTING_ACROSS_PACKS.md): each
pack is its own Valhalla build, so with no pack covering both ends (or with an end inside
another installed pack's margin, near a border) `computeRoute` stitches: chains of installed
packs joined by **crossings** (`<pack>.crossings.tsv` next to the tar: where a road from
motorway to tertiary crosses the pack's border, `scripts/routing/crossings.py`; by car only
motorway…secondary, by bike or on foot primary…tertiary), a matrix per pack border by
border (origin → seams, seams → seams for a pack crossed on the way, seams → destination;
a request that fails on one bad location is halved until it's alone), the cheapest sum
wins (`bestPath`), then one route per leg with the seam's heading, joined by `joinRoutes`
(the first leg's "arrive" dropped, the next leg's "depart" folded into the manoeuvre before
it), so guidance sees one route. Near a border both the single-pack route and the stitched
one are computed and the faster wins. A reroute on a stitched trip only recomputes the leg
to the next crossing ahead (`lastStitch`), unless more than 10 km off. `canRoute` (guidance's
gate) is true for a stitchable trip too. Valhalla's `max_matrix_distance` (`valhalla-defaults.json`)
is also where its matrix search gives up, not only a straight-line check: at 500 km a 472 km bike
leg came back empty (Ourense → Lisboa), so it is 4× the route reach by bike and on foot (2000 and
1000 km) and the route reach by car (5000 km). **Catalog**: `routing-manifest.json` in the
fixed release `routing-index` (override: `EXPO_PUBLIC_ROUTING_MANIFEST_URL`, set by
`scripts/e2e.sh` for its local pack server), cached in kv-store; each pack lists its tar
parts (≤ 1900 MiB, GitHub's asset limit is 2 GiB), a `.pois.tsv` and the search side
files: `.streets.tsv` (street and locality names: kind, name, lat, lon, name:es, name:en), `.places.tsv`
(every named POI whatever the map zoom: kind, name, other names, lat, lon, name:es, name:en; the two
trailing columns since 2026-10-29, ignored by older apps, which read the first four or five) and
`.addresses.tsv` (house numbers: street, number, lat, lon), both from
`scripts/routing/places.py` (packs built before 2026-10-26 lack them). `downloadPack` checks the room needed
up front and queues the parts, POIs and side files not on disk yet (a retry
only fetches what is missing) through the download manager (kind `route`). The
completion handler fails a file whose size differs from the manifest; when every part is
there it appends them into `<id>.tar.tmp`, checks the size, renames it, registers the
item, then deletes the parts and imports the POIs into `map_pois` / the search index
under `route-<id>` (`storeEmergencyPoints`, batched, shared with the Overpass sync), then
the street names into `map_places` / `map_localities` (`indexPackStreets`, batches of
5000 with a yield; source `route-<id>`, and a `map_sources` row with `index_version` so
search works with no map installed), the places (`indexPackPlaces`, source
`places:route-<id>`) and the house numbers (`indexPackAddresses`); all three are read
from the file in 4 MB blocks of whole lines (France's streets are 150 MB, Germany's doors
780 MB: one string would be several times that in Hermes). The map
index reads one zoom level under a tile budget, which for a big map holds only the main
roads and important POIs: the pack's files fill that in. Packs installed before the
catalog had a side file fetch just that file (`fetchMissingSideFiles`, after each catalog
refresh; the catalog refreshes 4 s after startup when a pack is installed). Search also runs the match restricted to 30 km
around the user, so a common street name nearby isn't lost among thousands. A
kill mid-assembly is recovered by the manager re-finalizing the last part (all parts are
still on disk); 4 s after startup `sweepRoutingFiles` deletes temp files and parts/POI/
street files no active download belongs to. size and sha-256 are verified (country download lifecycle above). Removing a pack closes the router
and drops its POIs. **Packs are built** by `.github/workflows/country-packages.yml` (monthly
+ manual): `scripts/routing/build-country.sh` per country of `packs.json` inside
`ghcr.io/valhalla/valhalla:3.9.1` (pinned by digest in `VALHALLA_IMAGE`) — Geofabrik PBF(s) (md5-checked; several are
`osmium merge`d: Spain + Canary Islands; `clip` cuts a bigger extract to the country's
`regions.json` bbox: Saudi Arabia from gcc-states, Caribbean islands from central-america)
+ admin boundaries (levels 2/4) from Overpass, by ISO 3166-1 at level 2, else at any level,
else ISO 3166-2 (territories: Puerto Rico, Aruba), else none (right-hand traffic)
(`scripts/routing/admins.sh`); refreshed monthly on the 1st by `.github/workflows/admin-boundaries.yml`
into the `routing-admins` release (`admins-<ISO>.osm.pbf`, or `.none`; 18 jobs, 3 at a time; a country
Overpass doesn't answer for keeps last month's file), read from there by the pack builds (a
country missing in it asks Overpass and is kept) →
`valhalla_build_admins` → `valhalla_build_tiles` (retried: 3.9.1 segfaults now and then)
→ one tar per country (the owner wants whole-country packs only) → emergency points
(`osmium tags-filter` + `emergency-points.py`, same columns as the Overpass TSV) → street
names (`streets.py`, one row per name per ~1 km) → split → `manifest.py` (bbox, cells,
parts with sha256; empty side files dropped).
The workflow keeps its token away from third-party code: checkouts don't persist
credentials, `GH_TOKEN` is only on the steps that call `gh`, and go-pmtiles is checked against
its SHA-256. The catalog steps tell "no index yet" (404) from any other `gh` failure
(`scripts/gh-releases.sh`), which stops the job: a catalog published without last month's
entries would drop every country the run didn't rebuild, and the prune would delete their files.
A map's fragment reaches the catalog only if its upload succeeded.
Each run gets its own tags, one per continent (`routing-YYYYMMDD-<run id>-<continent>`:
GitHub stops at 1000 assets per release), and each pack records its release,
so countries not rebuilt in a run keep their previous files (a rebuilt country replaces
all its packs; countries no longer in `packs.json` are dropped); `routing-index` is updated
last, and the run fails rather than drop countries if the previous manifest can't be
read. Before publishing, every pack's cells are clipped to its Geofabrik extract's
`.poly` (`manifest.py clip`: extracts keep whole ways that leave them, ferry lines above
all, which would make Ireland's pack "cover" Bilbao). Then releases that neither the new
nor the previous manifest points at are deleted. A country that gains a pack keeps its map
from an earlier run, with its own side files: `manifest.py unshare` drops those from
`maps-manifest.json`, so the app downloads and indexes the pack's only.

**Service roads on the map** (`style.ts`, `tameServiceRoads`): Protomaps draws every
`highway=service` almost like a street, private and underground ones included. The tiles
carry `access` and `is_tunnel` but not the service type or the layer, so private (`access`
private/no) and underground service roads are hidden and the rest drawn at half width;
an untagged garage ramp (`service=driveway` with no access, a `parking_aisle` with

**Compass beam** (`HeadingBeam.tsx`): while "show my location" is on and the Maps tab is in
front (tab `focus`/`blur`; a sheet over the map keeps it), a fan under the native puck
points where the phone points, like Google Maps': a symbol layer with a pre-drawn image
(narrow, or wide when the compass calibration is poor) rotated with `icon-rotate` in map
alignment, so it keeps its screen size and follows the map's bearing natively. Position
from MapLibre's `LocationManager` (the puck's engine), heading from
`expo-location` (`watchHeadingAsync`, redrawn every ≥ 2°) turned to the screen's top by
`heading.ts` (interface rotation from `expo-screen-orientation`: expo-location measures along the
portrait top, so landscape pointed 90° off; on iOS the orientation is UNKNOWN until the first
rotation after launch, so the heading is withheld in landscape rather than guessed; Android
re-reads it every 2 s; landscape-natural Android tablets stay 90° off). No compass, no beam (the iOS
simulator; the Android emulator has no rotation-vector sensor).

**Navigation view** (`FollowCamera.tsx`, `follow-core.ts`), Google Maps / Waze style:
guidance opens as a trip preview (the card: mode chips, first maneuver, whole route
framed above it, "Iniciar"). `startNavigation()` (store `navigating`, reset by
start/stop) switches `GuidancePanel` to a maneuver banner at the top (replacing the
search pill; regions/markers FABs hide) and a slim bar at the bottom (time left,
distance · arrival, directions, stop), and the camera follows the user, with the user
three quarters down the map between the search pill and the guidance panel (camera
padding from the panel's measured height). Plan and reasons: `docs/NAVIGATION_VIEW_PLAN.md`.
Guidance keeps a 30 s track of fixes (`pushFix`); `travelBearing` is the direction of the last
8/12/15 m (foot/bike/car), `movingBearing` prefers a car's GPS course and the track on foot.
Bearing (`followBearing`): on the route, the road's direction right where the user is
(`RouteProgress.roadBearing`, a chord a few metres behind to a few ahead of the snapped point, so
the map turns going round a corner, not before it), unless moving > 90° against it; off it, the
way the user moves; standing off the route the map holds (the compass only gives the first
bearing on foot). `smoothTurn` drops < 2° and caps the turn rate (90°/s, 60°/s on foot). Moving
> 120° against the road (`isWrongWay`) counts as off the route for rerouting. Every GPS fix is an
`easeTo` (linear) to where the user will be at the next fix: the snapped point moved along the
route by speed × the smoothed gap between fixes (`followCenter`, ≤ 60 m; off the route straight
on), lasting that gap, so the map glides without trailing a fix behind. Zoom by mode and speed
and closer before a maneuver (`followZoom`); pitch 45° car, 40° bike, 30° foot. While navigating
the route line starts at the snapped point (the travelled part is sliced off, like Google Maps';
not `line-gradient`, whose progress is projected and sampled into a texture). `fitBounds` on
MapLibre iOS fits at the current pitch and bearing, then applies the new ones: the overview
flattens first (`setStop`, 0 ms). Not MapLibre's `trackUserLocation`: on iOS it ignores the
padding (the user would sit under the panel) and turns by the raw course. The user is a
plain arrow view at the padded centre (`FollowArrow`), grey when the fix is worse than 50 m or none
came for 10 s while moving (standing brings none: the 3 m filter); on foot and by bike the compass beam is a view under it (`FollowBeam`); the
native puck and the map's beam hide meanwhile. "Norte arriba" (`map-north-up`, persisted
`navNorthUp`) keeps the map north up and turns the arrow with the direction of travel; its FAB
shows where north is. A pan/pinch (`onRegionWillChange` with `userInteraction`) stops following for
that trip (`Recentrar` pill brings it back); the route button in the FAB column
(replacing "my location") shows the whole trip flat and north-up. Stopping guidance
flattens the map. Following = `navigating` and not panned on this trip (`touchedFor`
holds the target).

**Guidance** (`guidance.ts`, `GuidancePanel.tsx`): a zustand store watches GPS
(`BestForNavigation`, 3 m) and the compass while a target is set and keeps the screen
awake. With a pack covering both ends it asks for a route (car / foot / bike chips) and
follows it: `routeProgress` snaps each fix onto the shape (searching forward from the
last segment), giving the next maneuver, distance to it and what is left (time scaled
from Valhalla's estimate); two fixes off the route (> max(40 m, accuracy ≤ 80 m)) trigger
a reroute, at most every 10 s. The map draws the route line and frames it on the first
route of each target and on a mode change. `maps/route-steps` lists the maneuvers. A
failed reroute keeps the old route; with no route, the store retries every 10 s (back on
a road, a fresh fix after a stale one — last-known fixes older than 2 min are ignored).
The start heading is the GPS course when moving (> 2 m/s), else the compass on foot or
bike. Without a pack, or when Valhalla finds no way, it falls back to the straight line: an arrow rotated by
bearing − heading (map bearing without a compass), distance + 8-point direction, time
at a nominal speed, and, where the routing catalog has a pack covering the target, a button that opens that
country's download (`maps/download`); installing a
pack mid-guidance retries the route (`retryRoute`). Arrival ≤ max(20 m, accuracy ≤ 50 m) from the target, with a haptic; at the route's end
(it stops at the road nearest the target) the last stretch switches to the arrow. A session counter drops superseded starts, a
request counter late routes. Turn-by-turn voice, background location and rerouting
polish are phase 3 (`docs/MAPS_NAVIGATION_PLAN.md`).
**Lifecycle**: `startGuidance()` is the single "take me there" entry (place card, saved places,
Emergencias, search); when location is denied it shows an alert with "Open Settings" instead of
doing nothing. Guidance ends by itself 60 s after arrival and the screen only stays awake while

### Assistant (`modules/nomad-llm`, `src/features/assistant`, `src/app/(tabs)/assistant`)
- `modules/nomad-llm`: `getSystemModelStatus()` → `{ status: available | notEnabled |
  deviceNotEligible | modelNotReady | unsupportedOS | unsupported,
  provider: 'apple' | null }`, `generate(requestId, { prompt, system?,
  temperature?, maxTokens? }, onDelta)` (events `onDelta {requestId, delta, reset?}` /
  `onDone` / `onError`), `cancel(id)`, `route(prompt,
  instructions)` → `{ search, query }` (iOS: guided generation with a `@Generable`
  struct, greedy; it once wrote Spanish queries for English questions, so `retrieve` drops a model query
  in another language than the question). iOS weak-links FoundationModels (iOS 26+). The module is Apple-only (no android/ folder):
  on Android the bridge isn't linked, the status is `unsupported`, `HAS_SYSTEM_MODEL`
  (`system.ts`) hides the system model in the models screen and onboarding, and a stale
  `aiModelId === 'system'` is reset at startup. The Android assistant uses GGUF models only.
- `models.ts`: curated GGUF list, URLs pinned to a Hugging Face commit with exact sizes:

  | id | Size | Min RAM | Context |
  |---|---|---|---|
  | `qwen3.5-0.8b-q4km` | 533 MB | 3 GB | 4096 |
  | `qwen3.5-2b-q4km` | 1.28 GB | 4 GB | 4096 |
  | `qwen3.5-4b-q4km` | 2.74 GB | 7 GB | 6144 |
  | `gemma-4-e2b-q4km` | 3.11 GB | 8 GB | 6144 |

  `modelFit(model, ramGB)` and `recommendModel(ram)` (largest Qwen that fits). Items are
  `kind: 'model'`, id = model id; `useSettings.aiModelId` is a model id or `'system'`.
  `rank` orders answer quality (Qwen3.5 0.8B 1, 2B 2, Apple FM and Gemma 4 E2B 3, Qwen3.5 4B 4;
  `modelRank`/`bestModel`): an installed model becomes the active one when it beats the current
  choice (or nothing usable is selected); the user's pick in the models screen stays until then.
  Removing the active model (or finding its file gone at startup) falls back to the best one left. `tools`: how the model calls
  search_library (`thinking` for Qwen3.5, which only calls tools with reasoning on;
  `direct` for Gemma 4). Catalog GGUF files copied into `content/models` by hand (exact
  name and size) are registered at startup, which is also how E2E seeds a model.
- `engine.ts`: one `Engine` interface over `SystemEngine` (~4k-token window) and
  `LlamaEngine` (llama.rn, chat template from the GGUF via `jinja`, thinking disabled,
  GPU layers on real iOS devices, CPU elsewhere). `engine.decides` says how the model
  chooses to search: `tools` (GGUF: pass 1 offers search_library — Qwen with thinking
  on, budget 256 tokens — and either answers or calls it; pass 2 answers from the tool
  result with `tool_choice: 'none'`), `router` (Apple FM: `route()`), or null (an engine that can't decide: heuristics). `withEngine(modelId, fn)`,
  `stopGeneration()`, `releaseEngine()`, `releaseIfModel()`. One engine alive at a time;
  released on background and after 4 idle minutes. Release is terminal (a `released` flag:
  `load`/`generate` return stopped afterwards), and the AppState background hook also ends the
  answer in progress (`chats.cancelAnswer`).
- Chat or search (`chats.ts` `answer()`, rules in `rag-core.ts`): library off or empty →
  plain chat. Otherwise `guessIntent` (small talk, thanks, "who are you", and requests
  about the previous answer such as "resúmelo" → chat) runs first on every engine; then
  the model decides when it can (`tools` / `router`, which also writes the query), and
  an engine that can't searches every question. The "Buscar en mi biblioteca" button
  forces a search (`searchLibraryFor`). The prompts were tuned on llama.cpp and Apple FM
  with a chat/search bench; the numbers are in the comments next to them.
- RAG (`rag-core.ts` pure + tested, `rag.ts`): question (or the model's query; `planRetrieval`: a
  model query replaces the question's words only with positive evidence of the question's language,
  `languageEvidence`; a short one with none, such as Apple's router's "meeting point" for "¿Dónde
  quedamos…?", is searched too but chunks are ranked against the question; positive evidence of another
  language drops it) → language detection and keyword queries (stopwords, light stemming, es/en; a follow-up such as
  "¿y cómo se trata?" inherits the previous question's keywords, `followUpTopic`, only when the
  question has at most one word of its own; the question's own queries are always searched; questions
  over 600 chars are searched once, after the sources, not twice) → libzim
  full-text search across archives, plus passages of the archives' PDF documents (the library's
  document index: up to 8, each page its own source with `page`, shown as "Título · pág. 12" on the chip
  and opened in the reader with the document's name, at its first page: WKWebView's PDF view ignores
  `#page=`), plus the family plan (`prepare/passages.ts`: one passage per filled section and one per
  person, in the question's language, labels carrying the words people ask with, "allergic", "dónde
  quedamos", but no topic words; source id `prepare:plan`, its chip opens the plan; the router and tool
  prompts name the plan, or "where do we meet?" was small talk), plus articles named after the question found by exact path
  (`buildTitleCandidates`: survival topics, word runs, the head word; ranked first and weighted when ranking
  chunks; reciprocal-rank fusion) → up to 6 distinct articles
  (redirects counted once) → chunks of 650 chars → BM25 (with title and search-rank
  boosts) → drop chunks sharing too few question terms (`relevantChunks`) → pack the
  best chunks into the model's budget as numbered sources → `[n]` citations, in the user
  turn (`sources` prompt) or as the tool result. Health questions get an extra caution
  rule.
- `chats.ts`: sessions/messages in SQLite, `useChat` store, `sendMessage` (token budget:
  answer 768 tokens for GGUF / 600 for system, ~25 % of the rest for history, the rest for
  sources, counting the whole RAG frame (`ragMessageFrame`); phases loading → thinking (router / tool decision) → searching → generating;
  throttled streaming), `stopAnswer`
  (also during search/load), only cited sources are kept on the message (`sourcesToShow`: if none is
  cited, none for a "not found" answer, else the top 3; PDF titles cleaned by `readableDocTitle`), answers to a deleted conversation are dropped. `searched` (in memory only) marks
  answers given without the library: the latest one shows "Buscar en mi biblioteca", which keeps
  the old answer until the new one is stored (restored if the new one is empty or fails). Native and
  llama.cpp errors map to translated keys (`errors.ts`: too long, declined, language, not ready,
  busy, quota, background, disk full, system update, empty); an empty answer shows `errors.empty`.
  New chat or opening another conversation leaves the answer in progress running: it is stored in
  its own conversation, its error (if any) only shows there, and the others show "Respondiendo en
  otra conversación · Ver" and can't send until it ends (one engine at a time); the conversations
  sheet marks it "Respondiendo…". Deleting its conversation stops it; so does leaving the app.
- UI: chat with streaming Markdown (`markdown.ts` parser, `ui/Markdown.tsx`), source chips
  → reader, stop, "use my library" toggle, starters, AI/health disclaimer; conversations
  sheet; models screen (system model status, downloads, fit badges).
- Dictation (`dictation.ts`, `dictation-core.ts` pure + tested): a microphone in the composer
  (`composer-mic`) with the OS's speech recognizer through `expo-speech-recognition`, always
  `requiresOnDeviceRecognition`: no audio leaves the phone and no model of ours is involved.
  Shown only where it can stay on the device: iOS asks `nomad-llm`'s
  `supportsOnDeviceDictation(locale)` (on a locale without on-device support iOS would silently
  use Apple's servers, and the library only checks the phone's own locale); Android needs API 33+
  (`createOnDeviceSpeechRecognizer`; below it the library would fall back to Google's online
  recognizer) and `supportsOnDeviceRecognition()`, and offers the system's language-pack download
  (`androidTriggerOfflineModelDownload`) when the pack is missing. Only the microphone permission
  is requested (on-device needs no speech recognition permission). Locale: the app language with
  the phone's region (`dictationLocale`, es-MX on a Mexican phone). Non-continuous: ends after a
  pause; the text goes after what was typed (`joinDictation`), live, and is never sent by itself.
  Typing, sending or leaving the app cancels it; results after a cancel are dropped.

### Preparedness (`src/features/prepare`, `src/app/(tabs)/(home)/prepare`)

Emergency plan and kit, inspired by "if the internet goes down" checklists: things a
downloaded library can't hold because they are the user's own. Entry: Home's "Mi plan
familiar" action and the plan/kit rows of "Tu preparación" (`features/home/readiness.ts`).

- Data (`types.ts`, `store.ts`): one JSON document in the kv-store key `prepare` —
  contacts, important numbers, people (medication, allergies, blood type), two meeting
  points (`primary`, `secondary`), home notes, household (adults ≥ 1, children, pets,
  days 3/7/14), kit entries by item id (`have`, `expires` "YYYY-MM", `note`,
  `reminderId`) and custom items (`custom-<uid>`). Nothing leaves the device except the
  PDF the user shares. No SQL tables (no migration to coordinate).
- Meeting points can link a map pin (`useMarkers` read-only); its lat/lon are copied so
  the plan keeps the place if the pin is deleted. "Show on map" uses `useMapUi.focus`.
- Kit (`kit.ts`, pure, tested): 29 template items in 8 categories (ids are stable keys —
  never rename), children/pet items only when the household has them. Quantities: water
  4 L/person/day + 1 L/pet/day, food 2000 kcal/adult and 1400/child per day, medication
  max(days, 30). Expiry: `soon` = this or next month, `expired` = earlier.
  `rows.ts` turns template + entries into translated groups and a summary.
- Reminders (`reminders.ts`): local notification at 10:00 on the 1st of the month before
  expiry (none if that moment has passed); permission asked the first time an expiry is
  saved; `planReminders` reconciles the scheduled set with the plan at startup, on foreground and
  when the household or language changes, through one queue; a notification tapped from a cold
  start waits for the navigator (`whenNavigatorReady`); Android channel `reminders`. The expo-notifications plugin has
  `enableRemoteNotifications: false`, so there is no push entitlement.
- Assistant (`passages.ts`, pure + tested): the plan as passages for the assistant's retrieval
  (Assistant, RAG); they only reach the prompt of the on-device model.
- PDF (`document.ts` pure + `share.ts`): A4 HTML (blank rows to fill by hand when a
  section is empty, then the kit checklist) → `Print.printToFileAsync` → renamed
  to "Plan de emergencia.pdf" in the cache → `Sharing.shareAsync` (print, Files, AirDrop). The
  exported PDF is deleted after sharing, on reset and at launch; the plan reads only its own
  kv keys.
- The hub also lists offline guides from the catalog (Ready.gov es/en, post-disaster,
  medicine, water, food preparation) filtered by content languages, with download buttons.

### Credits (`src/features/credits`, `src/app/settings/{credits,packages,license}.tsx`)
